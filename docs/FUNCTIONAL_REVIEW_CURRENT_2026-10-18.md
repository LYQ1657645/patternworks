## 需要修复的问题（本轮尚未修复）

### R1 — P1：过期或已删除的服务端会话仍能通过旧 cookie 读取数据

位置：[SessionAPIView.owner](../backend/processing/views.py#L42)。它直接读取 `request.session.session_key` 作为资源所有者，没有先访问会话内容触发 Django 的数据库加载和过期校验。

**隔离实测**：建立正常会话及数据集后，分别把服务端 Session 的到期时间设为过去、删除该 Session。使用独立 APIClient 重放旧 cookie，两种情况的数据集列表和详情均仍返回 200。另用启用 CSRF 校验的客户端，在会话到期后携带原有合法 CSRF token，诊断提交仍返回 202 并归属旧 owner；派发被 mock，没有执行真实任务。新会话读取原数据返回 404，因此问题是会话失效/撤销未被执行，不是任意跨会话读取。公网 Basic Auth 与 S3 凭证的独立过期检查仍存在；本轮没有绕过这些保护。

影响：泄露或应当撤销的会话 cookie，其读权限不能按服务端 Session 生命周期可靠撤销。浏览器自然删除 cookie 不能替代服务端校验。

建议：先让 Django 校验/加载会话，再确定 owner；失效记录应创建新会话或明确要求重建会话，不能继续使用旧编号。验收需覆盖过期、删除、无效 cookie、有效会话恢复和 CSRF，而非仅测试两个正常会话的隔离。

### R2 — P2：连接过期后直接导入仍显示 Connected

位置：[importFile](../frontend/src/App.tsx#L245)，对比同文件 `loadFiles` 的 410 处理。导入 API 对过期连接正确返回 410；导入提交的 catch 仅显示错误，没有清空 connection、文件、选中项或游标。

**受控前端实测**：执行当前 App TSX 的实际导入按钮处理器，模拟 `/datasets/` 返回 410。错误出现，但 Connected 标记和旧选择仍保留。隔离 API 请求同时确认过期导入返回 410 且不创建任务/数据集。这些前端探针使用 hook/API mock，不是完整浏览器 E2E。

建议：统一处理文件列表、直接导入及异步 IMPORT_DATASET 的 CONNECTION_EXPIRED；保留已有处理结果，清除失效连接状态并引导重连。验收包括列表已加载后等到过期再导入，以及排队期间凭证过期。

### R3 — P2：生命周期改变后，已打开的历史任务详情保留旧链接

位置：[TaskHistory 详情 effect](../frontend/src/TaskHistory.tsx#L18)、[刷新按钮](../frontend/src/TaskHistory.tsx#L57)和 [DatasetBrowser 回调](../frontend/src/DatasetBrowser.tsx#L47)。终态详情只在选中任务或主任务 ID/状态变化时重取；刷新按钮仅刷新列表；数据集 trash/restore 没有向历史详情传递刷新信号。

**受控前端/代码确认**：先缓存成功 CSV 任务详情，再发生数据集生命周期变化，点击 Refresh task history 并不改变详情 effect 依赖，旧下载链接仍存在。**隔离 API 实测**确认重新读取任务后 `dataset_available=false`，下载返回 410。后端保护有效，问题在前端缓存同步；恢复后也可能反向保留“不可用”状态。

建议：生命周期变更传播统一 revision；列表、终态详情、选中预览和导出状态分别失效刷新。管理面板/数据集列表同步已经实现，本问题是独立的历史详情状态。验收覆盖打开详情 → 删除/恢复 → 不刷新整个页面的链接状态，以及手动刷新详情。

### R4 — P2：过期导入任务仍被标为可重试

位置：[JobSerializer.get_retry_allowed](../backend/processing/serializers.py#L28) 与 [retry_job](../backend/processing/services/recovery.py#L110)。序列化器判断任务状态和数据集生命周期，但未判断导入所需 connection 是否有效。

**隔离实测**：一个以 S3_TEMPORARY 失败的 IMPORT_DATASET，在其连接已过期后，任务 GET 仍返回 `retry_allowed=true`；POST retry 随后正确返回 409，提示重连，且没有创建新任务。

建议：共享重试资格校验，返回清晰的不可重试原因和下一步。原始失败码不能决定凭证目前是否有效。验收需覆盖刚失败可重试、连接后来过期、密文已清除、Trash/PURGED、以及非导入任务不受 S3 过期影响。

### R5 — P3：README 仍含“保留策略仅手动”的过期说明

位置：[README 的 Spark/存储说明](../README.md#L139)。首页和生命周期报告已说明自动保留，但正文仍称 artifact retention manual。应统一当前能力、限制和历史快照入口；不修改旧实测记录。

## 后续完善的取舍

1. **先修 R1–R4、补 R5，再做 GitHub 交付。** 先保证失效授权、错误引导和生命周期状态一致；创建私有仓库仍需审查发布内容与凭证排除，不应提交 `.runtime` 或环境文件。
2. **补前端组件/浏览器自动回归。** 当前 14 项主要覆盖 API 错误和纯状态逻辑；本轮受控探针不能替代真实 React 调度、网络和浏览器交互。优先连接过期、503 失败任务、切换数据、Trash/restore、终态详情刷新和导出恢复；另补真实 XLS、移动布局及多会话并发。
3. **决定分布式验收边界。** 原题强调分区和 distributed，但没有指定机器数。现状满足使用 Spark 的分区执行示例，不能声称已验证跨主机。如果继续加强，可加入可选 Spark master/executor 配置与验收；需同时解决 loopback driver 地址、共享产物、资源与故障处理，不能只改 SPARK_MASTER。
4. **高基数 LLM 是能力扩展。** 501 个不同值会明确失败，即使总行数很少；一百万个重复值能运行不代表一百万个不同值能运行。先提供异步全列长度/distinct 分析与费用/预算提示，再考虑有上限的分批、持久检查点和取消恢复，保留明确同意，不能直接删限额。
5. **长期数据可找回与运维。** 修好 R1 后，浏览器 cookie 失效/清除会使旧 owner 的 Keep 数据无法在新会话找回，服务端又继续保留。长期使用需稳定身份/受控恢复、过期 owner 盘点和明确保留政策；不要为节省空间擅自删原始数据。备份、磁盘/队列/费用告警、限流和多用户负载属于进一步运营能力，原题未明确要求完整商业系统。
