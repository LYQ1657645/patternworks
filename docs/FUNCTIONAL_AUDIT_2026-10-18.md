## 确认的问题

### F1 — P1：长单元格的预览与实际替换不一致

位置：`backend/processing/services/datasets.py:238`，`backend/processing/services/rules.py:155`。

分页索引先把单元格截为 4,096 字符，正则预览随后对这个截断字符串执行匹配；实际 Spark 使用完整 Parquet 值。两种独立复现都失败：

- `a × 4096 + Z` 配合 `a$`：预览报告 1 个匹配，完整值是 0 个。
- 邮箱位于第 4,096 字符之后：预览报告 0 个匹配，完整值是 1 个。

这会让用户确认一个与实际执行不同的预览。建议为后台计算提供有界的完整样本读取路径（例如单独保存完整前 20 行或在 worker 读取 Parquet 样本），仅在最终展示阶段截断 before/after，并明确截断标识。不能仅把说明文字改成“预览可能不同”。

验收：完整值和预览计算的匹配数、是否匹配及变换结果保持一致；覆盖边界锚点、截断位置后匹配、增长超限和 Unicode。完整原值仍不发送给 regex 模型。

### F2 — P1：常见 Excel 日期无法接入日期标准化

位置：`backend/processing/services/datasets.py:39`，`backend/processing/services/date_policy.py:15`；XLS 也使用 datetime ISO 转换。

真实构造的 XLSX 日期单元格显示为 `2026-10-18`，导入值成为 `2026-10-18T00:00:00`。日期标准化只接受 date-only 字符串，因此独立验证器返回 `(null, invalid)`；即使模型给出正确日期，当前校验也不会接受。

建议保留 Excel 日期/时间类型或格式来源，在明确为日期的单元格上输出 date-only；对真实时间戳另设明确策略，避免为了修复而默默丢弃用户时间信息。需要同时处理现有已导入数据的兼容方式。

验收：真正的 Excel 日期单元格经过导入→预览→全列 Spark 转换得到正确日期；时间戳、闰日、空值及 1900/1904 日期系统有明确测试。

### F3 — P2：XLSX 末尾空表头与 CSV 的处理不一致

位置：`backend/processing/services/datasets.py:117`–`133`。

构造表头 `[Name, 空]`、下一行 `[Alice, useful value]`：openpyxl 的首行流式宽度为 1，代码据此锁定宽度，后续有效第二列触发 `ROW_WIDTH`。CSV 中相同的空表头可以自动命名；README 对空表头自动命名的表述也没有排除这种情况。

建议有界扫描/预处理真实使用宽度，或选择一致、明确的导入规范；不能静默丢掉后面的数据。继续防范恶意工作表维度及超宽文件。

验收：末尾/中间空表头、重复表头、稀疏行、格式化空列和超限列数均有一致结果。

### F4 — P2：取消任务的批量清理可能永远遗漏较旧记录

位置：`backend/processing/services/recovery.py:77`，`Job.Meta.ordering` 为创建时间倒序。

清理器每轮都选最近 100 个符合条件的 CANCELLED 任务，完成清理后不把记录移出候选集合。复现用 101 个过期取消记录，其中最旧一个有合成残留产物；连续执行三轮清理，该产物仍存在。实际触发通常需要取消后 worker 来不及自行清理、同时已有较多取消记录。

建议记录清理完成状态或使用可推进游标，保证每轮处理后候选集合前进，同时保留 attempt token 保护和任务审计记录。

验收：超过 100 个记录经过多轮全部清理；较新 worker 产物和 READY 源数据始终保留。

### F5 — P2：RE2 校验通过的模型结果仍会误匹配

位置：`backend/processing/services/rules.py` 的生成/校验流程；证据为本轮真实模型输出。

模型在以下两条请求中生成了缺少数字/token 边界的模式：

| 描述意图 | 实际生成 | 反例 | 当前错误匹配 |
| --- | --- | --- | --- |
| 04 开头、后接恰好 8 位数字的澳洲手机号 | `04\d{8}` | `04123456789` | `0412345678` |
| ORD- 加恰好 6 位数字的订单号 | `ORD-[0-9]{6}` | `ORD-1234567` | `ORD-123456` |

这两个结果在基础正例上通过，也通过 RE2 安全校验，但会部分遮盖一个无效的更长标识符。它不是灾难性回溯漏洞，而是语义准确性缺口；不能声称该模型的所有生成都失败。

建议增加代表性中英文正例/反例评估集，提示词明确整 token/数字边界，并允许用户提供少量“应该匹配/不应匹配”的例子进行本地校验。不要给所有模式机械添加 `\b`，因为 Unicode、标点及子串任务的语义不同。提示词变更需更新缓存版本。

验收：错误长度、前后缀、大小写、Unicode 邻接、多个匹配和无匹配都纳入；校验失败时不要显示语义已验证的结论。

### F6 — P2：HTTP 503 丢失已持久化任务，重试入口需刷新才出现

位置：`frontend/src/api.ts:123`–`133`，`frontend/src/App.tsx:200`–`207`，各提交面板的 catch 分支。

后端在 broker 不可用时返回 HTTP 503，响应中包含 FAILED 任务 ID 和 `retry_allowed=true`。前端 API 包装将它转换成只含文案的普通 Error，调用者只显示错误，不更新 Task activity。独立 Node 检查实际编译后的 `api.ts` 确认 ID/重试标志均丢失。因此已保存的失败任务无法立即在界面重试；刷新恢复最新任务后才可能看到。

建议保留结构化 API 错误中的 HTTP 状态、错误码及 job，提交失败但已建任务时更新任务面板。为错误返回但没有 job、网络中断、未知响应和合法 202 分别覆盖前端测试。

验收：模拟队列 503 后无需刷新就出现对应 FAILED 任务及重试按钮；恢复队列后新任务成功，原任务仍保留。

### F7 — P3：线上仍显示功能“尚未实现”的开发文案

位置：`frontend/src/App.tsx:293`、`650`；`backend/processing/views.py` 的 health phase。

本轮 Safari 刷新后仍显示 Transform & review “Next milestone”、scale validation & deployment “Coming next”、Day 5 / BUILD 0.5。实际上转换和公网部署均已完成。会误导评审对完成度的判断。

建议把工作流步骤与连接/数据/任务状态绑定，删掉已过期的开发里程碑占位信息；产品界面只显示用户下一步可以做什么。

## 功能范围与其他代码检查结论

- **G1：多列同一任务未实现。** API/模型/表单均只有 `column`，用户可逐列串联，但不能一次选择 Email 和 Notes。原文使用 column(s)，单列满足其中一部分；为了消除验收歧义，建议支持选定多列、每列预览和统计、同一原子输出。不要将现状直接等同于“原要求已全部覆盖”。
- **G2：日期/分类最多 500 个不同非空值，单值 1,024 字符。** 这是主动设定的可见保护，不是静默数据错误，但真实订单日期跨多年、客户反馈等很容易超限。百万行演示只是重复低基数数据。建议先做全列 distinct/长度分析和成本估计，再引入有预算的分批推理、可恢复检查点；不能只删除上限。
- **G3：没有验证真正跨机器 Spark。** 当前 master=local[2]、driver host/bind=127.0.0.1、产物为本地 Docker 卷；只改 SPARK_MASTER 不能完成多机扩展。原文未明确要求几台机器，但“distributed”是题目重点。应明确单机分区并行的交付边界；如要演示多 worker/executor，需补驱动可达地址、共享存储、调度和相关故障验收。
- **G4：历史浏览有限。** 数据集接口只有最新 25 个（包含失败项），任务列表只有最新 1 个，没有游标/搜索/完整历史入口。超过范围的产物不一定删除，但通过当前界面难以找回；会话过期后也不能凭原浏览器列表继续访问。
- **G5：结果导出、数据集删除/保留策略未实现。** 不是原文明确必交功能，但对真实使用价值高。建议提供带会话隔离的异步 CSV/Parquet 导出，并妥善处理 CSV 公式注入风险；删除/自动过期需保留父子数据依赖和明确操作提示。
- **G6：连接过期的界面状态存在代码路径问题。** 恢复最新 CONNECT_S3 成功任务时，App 会直接设置 Connected；文件列表返回 410 后仅设置错误，不清空 connection。可能同时显示已连接和请重连。此项为代码确认，本轮没有人为改变 Safari 会话来重放过期场景，建议增加状态回归并在 410 时清空失效连接状态。
- **G7：测试覆盖仍偏后端。** 所有普通自动测试使用 SQLite/内存缓存，真实 PostgreSQL/Redis由在线检查及历史故障脚本补充；不是 PostgreSQL 并发锁/多用户负载测试。前端没有 Vitest/组件测试。`.xls`、移动布局、长任务期间多用户访问、冷缓存高基数费用/耗时值得补充。
